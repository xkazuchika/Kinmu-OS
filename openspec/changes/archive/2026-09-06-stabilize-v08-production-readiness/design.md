## Context

See proposal.md — Why. Next.js standaloneとPostgreSQLを単一ホストのComposeで稼働させる。既存の統合テストはDBを初期化するため専用DBが必要。既存の画面テストはHTTPでアカウントを準備する。

## Goals / Non-Goals

**Goals:** 独自DB設定でも運用スクリプトが正しい対象を扱い、監視とCIの成功が実際の検証結果を表す。

**Non-Goals:** 業務機能追加、DBスキーマ変更、大規模リファクタリング、認証方式変更、リリース公開。

## Decisions

- DB名とユーザー名は`db`コンテナ内の環境変数を引用して利用する。ホストでenvファイルをsourceする方式は任意コード実行とComposeの変数展開差を招くため採用しない。
- バックアップはumask 077の一時ファイルへ書き、成功後だけハードリンクで完成名を公開する。完成名が衝突した場合は失敗し、既存ファイルを上書きしない。終了時は一時ファイルを削除する。mktempのランダム文字列はmacOSとLinuxで互換な末尾に置く。
- `/api/health`をDB readinessとして維持し、短命の専用接続でSELECT 1を実行する。接続・問い合わせを期限で打ち切り、接続を解放する。通常リクエストの共有プールを停止しない。正常200、障害503と固定JSON、Cache-Control: no-storeを返す。
- Vitest対象をTS/TSXへ拡張し、既存のJSX変換で実行する。CIはDB統合テストの後に別の空DBで本番ビルドを起動し、Playwrightを実行する。ローカルでは既存アプリを使う従来手順も維持する。
- 依存修正版を固定し、ロックファイルを再生成する。監査例外の追加で検知を消さない。
- OpenSpecは変更成果物に加えて実装完了後に主仕様へ同期し、変更は検証記録付きで残す。
- Docker更新検証で、通常の承認後に申請とケースの審査時刻が1〜3ms異なり、毎回実行する移行検査が停止する不具合を再現した。審査詳細の厳密比較は業務操作前のversion 0に限定する。移行はversion 0でバックフィルするため初期検査の厳密性は維持され、件数・状態・現行改訂・休暇予約は更新済みケースでも引き続き照合する。過去データの書換えや許容時間幅による曖昧な比較は行わない。

## Risks / Trade-offs

- DB一時障害でアプリもunhealthyになる → readinessの意味をREADMEへ明記する。
- 短命の監視接続が増える → 10秒間隔の既存ヘルスチェックを維持し、接続を必ず閉じる。
- CIのブラウザ検証時間が増える → Chromiumのみ、専用DBと単一workerで再現性を優先する。
- 推移依存の更新で互換性が変わる → 型・統合・画面・build・監査を更新後に実施する。

## Migration Plan

DBマイグレーションは追加しない。更新前バックアップを取得して既存の更新手順を実行し、health・ログイン・主要業務を確認する。アプリ切り戻し時もDBを変更する必要はない。本変更の検証には隔離したDB・Composeプロジェクトを使用する。
