## Context

Kinmu-OS v0.5は、月次勤怠を組織・対象月ごとの不変な締めリビジョンとして保存し、通常勤怠CSVと監査ログを出力できる。給与ソフトへの引き渡しでは、利用先ごとに異なる従業員コード、列名・順序、文字コード、時間表現へ表計算ソフト等で変換する必要があり、締めリビジョンとの対応、再出力の同一性、変換者を追跡できない。

対象は100名以下のセルフホスト組織である。給与サービス固有APIや給与計算エンジンを内蔵せず、月次締めスナップショットを一人一行の汎用CSVへ安全に変換する。既存の編集中月も出力できる通常勤怠CSVとは分離し、給与連携は締め済みリビジョンだけを入力にする。

## Goals / Non-Goals

**Goals:**

- 締め済みリビジョン、公開済みプロファイル版、従業員コード対応を固定した再現可能なCSV出力を提供する。
- 管理者がコードを書かずに列と許可済み変換を設定し、出力前に全行を検査・プレビューできるようにする。
- UTF-8 BOMとCP932を正しく生成し、CSV数式注入、引用符・改行、表現不能文字を安全に扱う。
- 月次再開・再締め後も過去の出力と監査証跡を保持し、どの締めリビジョンが給与処理へ渡されたか追跡可能にする。
- 組織境界、役割、楽観ロック、原子的保存、アクセシビリティ、セルフホスト更新・復元を既存規約に合わせる。

**Non-Goals:**

- 給与、税、社会保険料、割増賃金、法令適合の計算・判定。
- 振込データ、給与明細、年末調整データの生成。
- 任意JavaScript、SQL、テンプレート式、利用者定義プラグインの実行。
- 給与サービスとのAPI同期や認証情報の保存。
- 初期版での多数のベンダー固有プリセット。v0.6は汎用標準プロファイルと設定JSONの移出入を提供する。

## Decisions

### 1. 論理プロファイル、変更可能なドラフト、不変な公開版を分離する

`payroll_export_profiles`を組織内の論理プロファイル、`payroll_export_profile_versions`を公開版として持つ。編集はドラフト設定へ行い、検査成功後の公開操作で連番の不変版を作る。公開済み版を直接変更せず、複製または最新版から新しいドラフトを作る。既に出力へ使用した設定が後から変わらず、利用先の形式変更にも新しい版で対応できる。

各公開版は、エンコーディング、改行、ファイル名規則、順序付き列定義、変換設定を正規化済みJSONスナップショットとして保持する。列ごとの更新頻度は低く、一括検証・複製・ハッシュ化が中心であるため、列を個別テーブルへ正規化するより版全体の原子性を優先する。DB制約に加えてZodでスキーマ版、列数、名称長、重複列、許可ソース・変換を検査する。

代替案の「常に編集可能な1行JSON」は過去出力を再現できないため採用しない。「列ごとの完全正規化」は部分更新と版コピーが複雑になり、100名規模の読取性能上の利点が小さいため採用しない。

### 2. 従業員コード対応は論理プロファイル単位で保持し、出力時にスナップショット化する

`payroll_employee_mappings`は組織、論理プロファイル、従業員、外部従業員コード、楽観ロック用versionを持つ。組織・プロファイル・従業員、および組織・プロファイル・外部コードを一意にする。CSV一括設定は全行検査後に単一トランザクションで反映し、行ごとの部分成功を行わない。

コード対応は版を更新するたびに複製せず日常的に変更できる一方、出力実行時には対象従業員と外部コードを実行スナップショットへ保存する。これにより後日のコード変更が過去出力へ影響しない。従業員台帳の`employeeNumber`を暗黙の外部コードとして流用しない。

### 3. 出力ソースはサーバー定義の月次フィールドカタログに限定する

一行を締めリビジョン内の一従業員とし、外部従業員コード、対象年月、締めリビジョン、従業員・部署の固定表示情報、所定・実働・残業・休日勤務、休暇単位・対応時間、欠勤、残業申請差異件数など、スナップショットから再現できる型付きソースだけを公開する。列はソース値、固定文字列、空欄のいずれかを選ぶ。

変換は文字列、整数分、`HH:MM`、小数時間、日付・年月、真偽・区分の対応表に限定する。小数時間は整数分から10進演算で求め、桁数と`half_up`または`truncate`を設定・表示する。合計の再計算、条件式、列間参照、任意式は許可しない。利用可能フィールドはカタログのschema versionで管理し、古い締めリビジョンに値がない場合は必須列エラーまたは明示的空欄として扱う。

### 4. プレビューと生成で同じ純粋な変換パイプラインを使用する

ドメイン層は、締めリビジョン、公開プロファイル版、コード対応スナップショット、対象従業員フィルターから、中間の型付き行、検査結果、最終セル列を決定する純粋関数を持つ。プレビューは先頭行だけでなく対象全行を検査し、件数集計とページングされた表示行を返す。

生成APIはクライアントのプレビュー結果を信頼せず、組織・月のadvisory lockとトランザクション内で締め状態、期待リビジョン、プロファイル版、マッピングversionを再検査する。検査エラーが0件の場合だけ出力実行・監査記録を保存する。警告は種類と対象件数を確認ダイアログで明示し、確認済み警告コードを送信させて再検査する。

### 5. CSVは決定的に生成し、CP932は往復検査する

行順は外部従業員コード、Kinmu-OS従業員IDの順で固定し、列順は公開版へ固定する。RFC 4180相当の引用規則とCRLFを既定にし、UTF-8 BOMまたはCP932を選択する。CP932は変換前後の往復検査で表現不能・代替された文字をセル位置付きエラーにする。

テキストセルが空白除去後に`=`, `+`, `-`, `@`で始まる場合、生のまま出力しない。プロファイル列の方針を`reject`または`prefix_apostrophe`から選び、後者はプレビュー警告と監査要約に残す。数値型として検証された負数は対象外とする。固定値にも同じ検査を適用する。

CP932実装には`iconv-lite@0.7.3`を固定versionで使用する。MITライセンス、公開サイズ、更新状況を`encoding-japanese`と比較し、`cp932`で①・髙を含む日本語が往復一致し、表現不能な絵文字は往復不一致として検出できることを確認した。自前の文字コード表は保守リスクが高いため採用しない。

### 6. ファイル本体ではなく再生成に必要な不変マニフェストを保存する

`payroll_export_runs`は組織、対象月、締めリビジョン、プロファイル版、対象条件、コード対応スナップショット、検査要約、行数・列数・byte数、SHA-256、生成者・日時を追記型で保持する。CSV本体はDBへ保存せず応答時に生成する。

既存実行の再ダウンロードは保存済みマニフェストから生成し、SHA-256が一致した場合だけ返す。不一致は整合性エラーとして拒否・監査する。現在条件での再実行は別runとして保存する。同じ入力は同じbytesになるため、同一ハッシュでも各明示操作の監査runは区別する。

DBへのファイルblob保存はバックアップ肥大化と個人情報の複製を増やすため採用しない。外部オブジェクトストレージはセルフホスト構成を複雑にするため採用しない。

### 7. 再開・再締めは旧出力を無効化せず、対象リビジョンを明示する

月を再開しても過去の締めリビジョンと出力runは削除・更新しない。UIでは、現在の月状態または最新締めリビジョンと一致しないrunを「旧締めリビジョンの出力」と表示する。再締めで新リビジョンが作成されても自動出力せず、新しい検査と明示的な生成を要求する。

旧runの再ダウンロードは監査・照合目的で許可するが、「給与処理へ再利用する前に最新リビジョンを確認する」警告を表示する。旧runを最新として見せるより、履歴性と説明可能性を優先する。

### 8. 設定移出入はversioned JSONとし、個人対応を含めない

汎用標準プロファイルを初期ドラフトとして提供し、設定は`schemaVersion`付きJSONで移出入できる。JSONには列・変換・文字コード設定だけを含め、従業員コード対応、組織名、利用者、出力履歴を含めない。未知フィールド、未対応schema version、任意式、上限超過をプレビュー段階で拒否し、取込は新しいドラフトとして行う。

### 9. 所有者・労務管理者だけに許可し、組織IDはactorから導出する

設定、コード対応、プレビュー、生成、履歴、再ダウンロードは所有者・労務管理者だけに許可する。APIはorganizationId、actorIdをセッションから導出し、送信された従業員、締めリビジョン、プロファイル、runが同一組織であることをDB制約と処理の両方で検査する。従業員役割には件数、プロファイル名、外部コードを含め存在を露出しない。

## Risks / Trade-offs

- [給与ソフトごとの差が汎用設定を超える] → v0.6は月次一人一行と許可済み変換に限定し、実例から需要が確認できた形式を後続プリセットまたは別changeで追加する。
- [誤った列対応でも構文上は有効] → 列型、単位、サンプル値、全件プレビュー、必須列、警告確認、プロファイル公開前テストを要求する。
- [CP932変換で情報が失われる] → 往復不一致をエラーにし、UTF-8 BOMへの切替か元データ修正を案内する。
- [小数時間の丸めが給与結果へ影響する] → 桁数・方式を版へ固定し、変換前分数と変換後値をプレビューし、給与計算ではない旨を表示する。
- [外部従業員コードが個人識別子になる] → 組織境界、管理者限定、監査、ログへの生値非出力を徹底する。
- [再生成ロジック変更で過去hashが一致しない] → マニフェストへgenerator schema versionを保存し、互換生成器を保持する。非互換変更時は過去runを閲覧可能に保ち再ダウンロード不可理由を明示する。
- [JSONスナップショットが肥大化する] → 100名・月次一行を前提に列数、文字列長、run対象数へ上限を設け、性能試験でDBサイズと生成時間を確認する。

## Migration Plan

1. 加算的migrationで新テーブル、制約、索引、組織境界トリガーを追加する。既存勤怠・締め・通常CSVは変更しない。
2. 既存組織ごとに未公開の汎用標準ドラフトを一件作成する。従業員コード対応や出力runは自動作成しない。
3. v0.5バックアップを空DBへ復元してmigrationを適用し、既存締めリビジョン・通常CSV・ログインが不変であることを確認する。
4. 管理者がドラフト、コード対応、プレビューを確認し、プロファイルを明示的に公開してから初回出力する。
5. 更新前バックアップへの復元を正式なロールバックとする。v0.6テーブルを持つDBへv0.5アプリを接続した場合、給与連携機能は利用できないため新規入力を止め、原則として更新前バックアップを空DBへ復元する。

## Open Questions

実装を阻害する未決事項はない。特定給与ソフト向けプリセット、API連携、日次複数行形式はv0.6の実利用例を集めて別changeで判断する。
