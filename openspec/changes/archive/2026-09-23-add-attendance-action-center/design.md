# Design

## Context

動機と対象は proposal.md を参照する。現在は `projectOperationalAttendanceMonth` が在籍履歴・カレンダー・休暇・欠勤を合成し、`listApprovalInbox` が期限と担当の適格性を表示する。ホームの `monthlyWorkflowProgress` は月次工程を案内している。通知は申請操作内で生成され、`notifications.eventKey` の一意制約でイベントの重複を防ぐ。

本番はNext.js standalone appとPostgreSQL、使い捨てmigratorのCompose構成で、定期workerは存在しない。`scripts/update.sh` はmigratorとappだけを更新する。このため、画面追加に加え独立した定期実行・更新経路が必要になる。

## Goals / Non-Goals

**Goals:**
- 勤怠の正本と承認規則を再利用し、ホーム・一覧・通知で同じ対象を判定する。
- 通知は派生した案内として追加し、打刻・申請・締め・監査の業務結果を書き換えない。
- UIリクエストや単一プロセスの寿命に依存しない日次重複防止を実現する。

**Non-Goals:**
- 汎用タスク管理、手動完了、スヌーズ、段階的エスカレーション、ユーザー別通知時刻設定。
- メール等の外部通知。今回の「通知」は既存受信箱への保存を意味する。
- 新しい法令・休暇付与・締め期間ルールの導入、既存承認権限の拡張。

## Decisions

### 1. 正本から読み取る共通判定サービス

`src/lib/attendance-action-center.ts` を追加し、組織、現在時刻、閲覧actor、絞り込みから事項を取得する。テスト可能な時計を渡し、既存の勤怠投影にも必要最小限の任意の現在時刻引数を追加する。種類は `open_punch`、`unresolved_day`、`overdue_approval`、`returned_request` とする。

勤怠は有効カレンダー開始月と既存打刻の最古月から当月までの候補を作り、締め済み月を除き、月単位で既存投影を再利用する。未解決日は投影結果と過去日条件で選別する。承認は現在の `pending && dueAt < now` または `returned` を選ぶ。未退勤と未解決は同一従業員・同一日で重複させず、承認事項はケース単位とする。複数日休暇はケースの対象開始日を一覧・月フィルターに使い、詳細には全対象日を表示する。

古い未締め事項の見落としを防ぐため、固定の30日・90日制限は設けない。既定表示は全対象、月フィルターは明示的に適用する。月ごとの処理・集約でメモリを制限し、対象日のN+1クエリは作らない。最初から派生タスク表を永続化する案は、解消の同期漏れと二重の正本を生むため採用しない。

APIの行・件数・ホーム要約は同一の取得スナップショットから返す。ホームは要約だけ取得し、一覧はサーバーで50件にページ分割する。期限超過、再申請待ち、未退勤、未解決の順、次に期限または対象日昇順、最後に安定IDで並べる。内部IDは種別＋従業員・日付、または種別＋ケースIDで構成する。集計前に認可する。

### 2. 閲覧できることと実行できることを分ける

従業員は本人分、approverは本人分と現在担当の期限超過、管理者は組織分を閲覧する。本人の期限超過は「承認担当者の対応待ち」と表示し、本人に審査を促さない。無効化された利用者へ通知しないが、その従業員の過去日の不備は管理者から隠さない。

申請の閲覧、再申請、代理操作、審査、再割当の可否は既存サービスの規則を抽出・共有して使う。自己審査や期限切れの引継ぎを新しい一覧から迂回できないようにする。返却事項の操作担当は対象本人と、既存の再申請権限を持つ代理作成者とする。本人の修正が必要な事項も管理者には「本人の対応待ち」として見せる。

関連するpending修正・休暇ケースを取得し、元の不備は解消まで保持しつつ「審査待ち」と詳細導線を示す。対応ボタンは新しい申請を重複作成するショートカットにしない。

### 3. 既存UIを利用する要対応画面

`/action-items` と読取API `/api/action-items` を追加する。既存のPageHeader、FilterBar、StatePanel、一覧・カードを用い、ホームには種類別件数と一覧リンクを置く。画面カタログと役割別ナビゲーションに登録する。

APIはキャッシュ禁止とし、対象月・種類・部署・従業員・ページを検証する。許可範囲外のフィルターは拒否し、候補を漏らさない。既存の `navigation-context.ts` に安全な戻り先と条件を登録し、勤務日・月・対象者を指定した実績、修正、申請、審査へ誘導する。既存画面が指定日を開けない部分は、この導線の受入れまで今回の変更に含める。

0件、検索結果0件、読込中、取得失敗を区別する。既存のホームの打刻・月次工程を維持して要対応の入口を追加する。320pxとキーボード操作を受入れ条件とする。

### 4. 1日1件の汎用ダイジェスト

通知種別 `action_items_reminder`、対象種別 `action_center`、対象IDに受信者のuser IDを使う。既存 `eventKey` へ `action-reminder:<organizationId>:<userId>:<localDate>` を保存し、通知と重複防止を同じINSERTで確定する。本文は「対応が必要な勤怠・申請があります。要対応一覧を確認してください。」程度とし、固定した氏名・件数・申請理由を含めない。

開く際は受信者と現在セッションを検証して `/action-items` へ移動する。解消済みなら空表示、役割変更後なら現在のスコープに縮小する。通知日と既読状態は履歴として保持する。

workerは15分間隔で現在状態を検査する。組織現地9時以降、その日に未送信で日次対象がある有効な利用者へ保存する。差し戻し日には即時イベント通知が既にあるため、現在の差し戻しイベント日時を承認履歴から取得し、翌日から催促する。初回提出日時を代用しない。

管理者は組織内対象、一般従業員は自分の勤怠・差し戻し、approverはそれらと現在審査できる期限超過を対象にする。本人には他者の審査を待つだけの期限超過で日次催促しない。対象が複数でも一つにまとめる。9時以降に新規対象が発生した未通知者には次回tickで作り、当日通知済みなら翌日以降とする。

組織単位のDB advisory transaction lockでworker同士を排他し、DB一意制約も維持する。組織の処理が失敗したらその組織の通知生成をロールバックし、他組織の処理は継続する。業務操作とは判定時点が競合し得るため、本文は最小限とし開いた時の再取得を正とする。監視用途の時刻・件数・安全なエラー分類をログへ残し、資格情報や理由本文は出力しない。

### 5. 専用workerと運用経路

`src/workers/action-reminders.ts` に `--once` と常駐ループを用意し、Nodeプロセスの終了通知で待機とDB接続を閉じる。組織ごとのタイムゾーンを使用し、過去の通知日の穴埋め処理はしない。日時はUTCの24時間加算でなく組織現地日付で判定する。

Dockerfileに、現行migratorと同じ依存・ソースを使用する非rootのworker targetを追加する。ComposeのworkerはDBと移行成功を待ち、公開ポートを持たず、restartを設定する。開発起動と単発検証はpackage scriptsで提供する。追加のキューブローカーや公開cron APIは作らない。

workerは直近tick結果・最終成功時刻を専用のローカル状態ファイルへ原子的に記録し、ヘルスチェックは失敗状態または最終成功から30分超で異常を返す。起動猶予を設ける。障害時もループは次回tickで再試行する。一回実行の失敗は非ゼロ終了とする。appのDB readinessとは独立して監視できるようにする。

`scripts/update.sh` は全イメージのビルド後に既存workerを停止し、移行成功後にappとworkerを入れ替える。移行失敗では旧appを維持し、旧workerを自動で新スキーマへ接続し直さず停止状態と復旧手順を明示する。初導入でworkerが存在しない場合も扱う。バックアップは通常のDBバックアップに日次キーを含み、復元中はworkerを停止する。

## Risks / Trade-offs

- 古い未締め月が多いと判定量が増える → 月単位の処理とクエリ共有、100名×3か月・300ケースのfixtureで一覧／ホーム集計を各5秒未満、1組織のworker実行を30秒未満で検証する。長年未締めの運用は別途時間を実測・明記し、切り捨てで解決しない。
- 通知直前に業務が解消する競合 → 通知は現在の未解消を保証する文面にせず、遷移時の現在状態を表示する。
- 多数の過去データが初日に対象になる → 利用者ごとに1件へ集約し、日付別の過去通知を生成しない。
- worker追加による更新漏れ → 更新スクリプトとComposeの実測を受入れ対象にし、appだけのビルド成功で完了にしない。
- 組織タイムゾーン変更で同じUTC日に現地日付が変わる → 重複防止の基準は現地日付と明記し、各処理開始時に時刻を固定する。

## Migration Plan

1. 通知enumの追加と必要な検索索引を加算マイグレーションで導入する。enum追加とその値を使う処理のトランザクション境界を確認する。既存通知・業務データは書き換えない。
2. v0.8相当DBで移行・再実行・既存申請通知・締め・給与CSVを検証し、新しいUIとworkerを配布する。
3. 隔離Composeでログインなしの通知、再起動、並行実行、DB障害復旧、更新・バックアップ復元を検証する。
4. 切り戻す場合はworkerを停止し、更新前バックアップを空DBへ復元してv0.8のCompose構成で起動する。新通知種別を含むDBへ旧appを接続する運用は保証しない。
