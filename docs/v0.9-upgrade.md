# Kinmu-OS v0.9.0 更新ガイド

## 対象と変更点

v0.8.0のセルフホスト環境をv0.9.0へ更新する所有者・運用担当者向けです。DBマイグレーション0018は日次「要対応」通知の種別を追加し、通知の受信者・参照先と組織の整合性を検査するトリガーを更新します。既存の勤怠・申請・通知を削除したり、既存通知の既読状態を書き換えたりしません。appに加えて、日次通知を作るworkerが稼働します。

## 更新前

1. 申請・審査、打刻、月次締め、給与CSV生成を止める保守時間を確保します。更新スクリプトはビルド中と移行中も旧appを維持するため、利用者への操作停止を案内してください。
2. `BACKUP_DIR=/secure/backups scripts/backup.sh` で更新前DBをバックアップし、別ホストまたは暗号化ストレージへ複製します。ファイルが空でなく権限が600であることを確認します。
3. v0.8.0のソースまたはイメージ、Compose設定、`.env.production`の安全な控えを保持します。セッション秘密鍵などをリリース記録へ転記しないでください。
4. `/api/health`、組織別の申請・通知件数と通知の既読件数、直近の締めリビジョン・給与run件数を記録します。別の空DBでバックアップの復元と旧版起動を試せる状態にします。
5. app・worker・migratorのビルドに必要なメモリとディスクの余裕を確認します。メモリ約2GiBの検証用VMでは、他のサービスと同時に新規appをビルドすると停止しました。

## 更新

1. v0.9.0のソースまたはリリースへ切り替え、`.env.production`の`APP_VERSION=0.9.0`と`SOURCE_CODE_URL`を配布版に合わせます。
2. `scripts/update.sh`を実行します。app・worker・migratorのビルドが完了してからworkerを停止し、マイグレーション成功後にappとworkerを入れ替えます。
3. ビルド失敗時は旧サービスが維持されます。移行失敗時は旧appが残り、workerは停止したままです。ログを保全して原因を修正して再実行するか、下記の切り戻しを行ってください。

## 更新後の確認

1. `docker compose --env-file .env.production -f compose.production.yaml ps`でapp・DB・workerのhealthを確認し、`/api/health`が200を返すことを確認します。
2. 所有者、承認担当者、従業員でログインし、ホームと「要対応一覧」を開きます。本人分、担当分、組織全体の表示範囲と、対象の勤怠・申請画面への遷移を確認します。
3. 既存申請・通知の件数と既読状態、直近の締めリビジョン・給与runを更新前の記録と照合します。worker起動後に新しい日次通知が加わる場合は、その件数を区別して照合します。
4. workerのhealthとログを確認します。日次通知は組織の現地時刻9時以降に対象利用者へ1日最大1件です。画面で通知を開く際に現在の権限を再検査します。
5. [業務の全体フロー](user-guide/workflow.md)に沿って、申請から承認、締め、CSV出力までの主要操作を確認します。

## 切り戻し

v0.9で変更したDBへv0.8アプリを直接接続しないでください。

1. v0.9のappとworkerを停止し、障害調査用に現在のDBとログを保全します。
2. 別の空DBを用意し、`CONFIRM_RESTORE=EMPTY_DATABASE scripts/restore.sh <v0.9更新前バックアップ>`で復元します。復元先を指すCompose設定と環境変数を使い、既存DBへ上書きしないでください。
3. 保持しておいたv0.8.0のソースまたはイメージ、Compose設定、環境変数でappを起動します。v0.9のworkerは起動しません。
4. `/api/health`、ログイン、申請・通知と既読件数、勤怠、直近の締めリビジョン・給与runを確認してから利用者へ再開を案内します。

更新後に行われた打刻・申請・審査・日次通知などは更新前バックアップに含まれません。切り戻し時は失われる操作の範囲を確認し、利用者へ伝えてください。
