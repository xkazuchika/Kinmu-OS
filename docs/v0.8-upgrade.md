# Kinmu-OS v0.8.0 更新ガイド

## 対象

v0.7.0のセルフホスト環境をv0.8.0へ更新する所有者・運用担当者向けです。v0.8は承認ケース、改訂、経路、引継ぎ、割当履歴、通知一意キーを追加する加算マイグレーションです。

## 更新前

1. 申請作成・審査・月次締め・給与CSV生成を止める保守時間を確保します。
2. `BACKUP_DIR=/secure/backups scripts/backup.sh` でPostgreSQLカスタム形式バックアップを取得します。
3. バックアップを別ホストまたは暗号化ストレージへ複製し、ファイルサイズと権限600を確認します。
4. 現在のアプリバージョン、コミット、Compose設定、申請状態別件数、直近の締めリビジョン、給与run件数を記録します。
5. 復元先に使う空DBとv0.7のCompose設定を保持します。

## 更新

1. v0.8.0のソースまたはリリースへ切り替えます。
2. `scripts/update.sh` を実行します。migratorが成功するまでアプリコンテナは入れ替わりません。
3. マイグレーションは既存の勤怠修正・休暇・残業／休日出勤申請を、初期改訂付き承認ケースへ一対一でバックフィルします。
4. 既存`pending`は担当を推測せず、所有者・労務管理者が扱う管理者共通プールへ置きます。既存の最終状態、審査者、コメント、日時、取消日時は維持します。
5. 起動前検査がドメイン申請件数、状態別件数、一対一、現在改訂、審査情報、休暇予約を照合します。不一致時は公開を止め、ログを保全してください。

## 更新後の確認

1. `/api/health`、所有者ログイン、従業員ログインを確認します。
2. 「承認受信箱」で既存申請の総件数と状態別件数を更新前記録と照合します。
3. 勤怠修正、休暇、残業／休日出勤の各ケースで第1版、審査結果、対象日を確認します。
4. 通知・監査ログ・休暇残高・直近月の勤怠・締めリビジョン・給与プロファイルとrunが維持されていることを確認します。
5. テスト用従業員で提出→差し戻し→再申請→承認→通知の往復を行います。

## 承認経路を段階的に有効化する

1. まず利用者へ「承認担当者」役割を付け、本人向け勤務機能が維持されることを確認します。
2. 一つの部署・一つの申請種別だけ、将来または当日の適用開始日で経路を追加します。
3. 新規申請が担当者へ届き、既存申請は暗黙に移動しないことを確認します。
4. 問題がなければ部署・申請種別ごとに範囲を広げます。
5. 経路未設定、自己審査になる経路、無効担当は未割当になります。「承認受信箱」で未割当と要再割当を毎日確認します。

## 切り戻し

v0.8で変更されたDBへv0.7アプリを直接接続しないでください。

1. v0.8環境を停止し、障害調査用にDBとログを保全します。
2. 別の空DBを用意し、`CONFIRM_RESTORE=EMPTY_DATABASE scripts/restore.sh <v0.8更新前バックアップ>` で復元します。
3. v0.7のソース、イメージ、Compose設定、環境変数で起動します。
4. `/api/health`、ログイン、既存申請件数、勤怠、休暇残高、直近の締めリビジョン、給与プロファイルとrunを確認します。
5. DNSまたはリバースプロキシを切り替える前に、復元環境の組織とデータ件数を再確認します。

v0.8更新後に作成された承認経路、引継ぎ、改訂、代理申請、通知は更新前バックアップに含まれません。切り戻し判断時に利用者へ影響範囲を伝えてください。
